ConnectWise Cloud Backup supply chain compromise

Stolen vendor app credentials for ConnectWise (ex-SkyKick) multi-tenant M365 applications were used from October 15 to mint Graph tokens across ~2,250 tenants (Microsoft; Huntress counted 300+ successful of ~1,000 observed). Microsoft attributed the campaign to Storm-0940 on October 21, operating the ARTEX agentic-AI framework.

On Cutsign: brief story 10-19 Storm-0940 attribution 10-22 CISO card IoC cards news & updates (live)

Verdict: hunt now if the ConnectWise app IDs ever touched your tenant — including former customers. This is credential abuse of a vendor's multi-tenant apps, not a patchable CVE: there is nothing to scan for, only logs to review. Sophos reports the token sweep reached tenants with no active backup subscription, so past use counts. ConnectWise disabled the seven app identities, but previously issued tokens may remain usable until they expire, and attacker persistence (added credentials, role grants) survives the vendor-side fix.

30-second read

Password spraying (151,000+ failures, Oct 10–14) preceded abuse of stolen ConnectWise application credentials from Oct 15: service-principal sign-ins from attacker infrastructure minting Graph tokens in customer tenants. Follow-on activity where sign-ins succeeded: directory reconnaissance, new client secrets planted on other applications (persistence beyond the ConnectWise apps), and privileged role changes including a service principal self-assigning Global Administrator. Conditional Access policies scoped to users often do not evaluate multi-tenant service-principal sign-ins — check yours rather than assuming coverage.

Infrastructure & discriminators

  • Token abuse: 144.172.64[.]128 · 144.172.64[.]99 · 144.172.64[.]60 · 144.172.94[.]243 (FranTech/PONYNET and related VPS)
  • Password spray: 187.15.88-90[.]x range, Oct 10–14
  • Suspicious-leaning user agents: Python-urllib/3.12 (enumeration and escalation tooling), python-requests/2.31 and 2.34.2 (targeted sweeps; the Oct 10–14 spray), curl/7.88.1 (Debian 12 python:3.12 container), azure-toolkit/1.0 (listed by Microsoft, not seen by Huntress) — expected vendor traffic is kiota-dotnet from Azure private IPv6. One Oct 13 browser user agent was missing its (KHTML, like Gecko) segment — a hand-set string
  • Low-confidence link: 194.165.16[.]21 (Huntress, on reuse of python-requests/2.31 only)
  • Operator tempo (Huntress, Oct 26 — scripted, with something adapting between runs): token requests to ~1,000 tenants one to six minutes apart (06:13–08:46 UTC Oct 15); ~100 failed token requests inside 10 s (06:04); a six-resource probe at exactly 4 s per tenant (13:54); credential replay at 13–21 requests/s against a 100-tenant list; post-change requests every 4–8 s for 22 min. Sub-second timestamps make these visible; minute-rounded exports hide them
  • Raw values: IoC corpus cards (16 + 11 indicators across the two stories)
  • All-zeros ServicePrincipalId (00000000-0000-0000-0000-000000000000) is Microsoft-documented service-principal-less authentication: "the service principal ID of an application making a service principal-less authentication is shown as 00000000-0000-0000-0000-000000000000 in the sign-in logs of the resource tenant" (Entra docs). A multitenant app obtains an app-only token from a tenant where it has no service principal object — no consent, no object ID claim, and in Microsoft's words "in most cases … harmless", except "where the target API has implemented improper authorization checks". That is the mechanism behind Chorus Cyber's observation: the campaign's token requests appear in tenants that never consented Cloud Backup; Chorus excludes those rows as noise. Read it the other way too: an all-zeros sign-in followed by successful Graph activity for the same appId is exactly the "improper authorization checks" case Microsoft warns about, and is a finding (inferred test below). Unresolved: Microsoft's retirement blocks SP-less auth for all non-Microsoft multitenant apps after March 31, 2026 (apps seen Feb 11–Mar 11 2025 were allowed until then; most others frozen April 2025; the Entra blog's timeline says the March date blocks "all client apps without a service principal ... including the ones previously allowed to continue working", while Microsoft's monitoring FAQ, updated since, still says tokens are issued "except for a few Microsoft and non-Microsoft applications") — all-zeros successful sign-ins for a third-party app in October 2026 should therefore be rare. Either enforcement is incomplete, the app is one of the FAQ's exceptions, or the logged rows are blocked attempts (check resultType). Both of Microsoft's freezes were scoped per resource, so an exception is a client-and-resource pair: keep the resource column when you inventory these. A "Success" row is issuance, not access: Inforcer (Oct 17) saw Graph issue the token with no permissions while Exchange Online and SharePoint Online rejected it with "missing service principal", and the Office 365 Management APIs (in Huntress's six-resource probe list) refuse any token lacking ActivityFeed.Read with error AF10001; none of those rejections write a tenant-side log. The companion note has the claim-by-claim table, sourced from Microsoft's token sample, Entra blog, claims reference and Q&A, with Inforcer and Huntress for the per-resource rows. Microsoft first-party apps still authenticate SP-less by design and show in user (mostly non-interactive) sign-in logs — expected, not this campaign; those records carry the user's device IP, so non-Microsoft ASNs there are normal. The question that matters is the service-principal (app-only) tab: all-zeros sign-ins whose appId resolves to a non-Microsoft publisher are grandfathered SP-less apps — a short, finite list worth a watch list

Inferred detections — no Sentinel? same hunt, generic

The published queries above come first — Microsoft's KQL and the ConnectWise guide checklist supersede everything here. This is the fallback translation for environments without Defender XDR / Sentinel tables, over exported Entra logs in any SIEM or even a spreadsheet:

Service-principal sign-ins — the core question, tool-agnostic:


# exported Entra SP sign-in logs, Oct 1 → now
appId IN (the seven appIds above)
AND NOT (source = Azure private IPv6 AND user_agent = kiota-dotnet)
→ review every remaining row; Python/curl UAs from VPS space is the campaign

Persistence audit — a service principal doing admin things is the tell:


# Entra audit log, Oct 13 → now
operation IN ("Add service principal credentials", "Add member to role",
  "Update application", "Consent to application")
AND initiated_by is a service principal (not a user)
→ every hit gets a human review; self-role-assignment = incident

# Splunk (Azure Monitor diagnostic export shape: category / properties.*; tune field
# names to your add-on). Includes the REMOVE and DELETE operations: Huntress's Oct 26
# telemetry shows the persistence as churn and cleanup, not just additions.

index=* category=AuditLogs earliest=-30d@d
    operationName IN ("Add service principal credentials", "Remove service principal credentials",
      "Update application – Certificates and secrets management",
      "Add member to role", "Remove member from role",
      "Add app role assignment to service principal",
      "Update application", "Consent to application",
      "Remove service principal", "Delete application")
    properties.initiatedBy.app.servicePrincipalId=*
| rename properties.initiatedBy.app.displayName as actor_app,
    properties.initiatedBy.app.servicePrincipalId as actor_sp,
    properties.targetResources{}.displayName as target
| stats count values(target) as targets min(_time) as first max(_time) as last
    by actor_app actor_sp operationName

# churn: the same target gets an add AND a remove of credentials or roles inside 60 min

index=* category=AuditLogs earliest=-30d@d
    operationName IN ("Add service principal credentials", "Remove service principal credentials",
      "Add member to role", "Remove member from role")
| rename properties.targetResources{}.displayName as target, properties.initiatedBy.app.displayName as actor_app
| eval verb=if(match(operationName, "^Add"), "add", "remove")
| transaction target maxspan=60m
| where mvcount(mvdedup(verb))=2
| table _time duration target actor_app operationName
→ any churn pair is a hands-on operator (or an agent retrying); a failed cert upload followed by
  a successful one within a minute is the same tell

# sibling-principal grant + cleanup: role granted to one principal, then another principal deleted

index=* category=AuditLogs earliest=-30d@d
    operationName IN ("Add member to role", "Remove service principal", "Delete application")
| rename properties.initiatedBy.app.displayName as actor_app
| transaction actor_app maxspan=30m
| where searchmatch("Add member to role") AND (searchmatch("Remove service principal") OR searchmatch("Delete application"))
| table _time duration actor_app operationName

# THE SIGN-IN RECORD: Azure Monitor table AADServicePrincipalSignInLogs has column
# AppOwnerTenantId, "the tenant identifier of the owner of the application" (confirmed against
# the Learn schema page Oct 27). Graph API: signIn.appOwnerTenantId exists on BETA only — a v1.0
# pull will not have it. Event-hub/Splunk key `properties.appOwnerTenantId` is inferred from the
# column name (Microsoft documents no sample record); tune to your add-on. Use it there — an
# SP-less app has no service principal in your tenant to look up, and the MicrosoftGraphActivityLogs
# schema has no owner or publisher column at all. Microsoft tenants (per Microsoft's own
# verification page, which lists them as "some, but not all"):
#   f8cdef31-a31e-4b4a-93e4-5f571e91255a  = "the Microsoft Service's Microsoft Entra tenant ID"
#                                            (Microsoft names no example apps for it)
#   72f988bf-86f1-41af-91ab-2d7cd011db47  = tenant of "Microsoft tenant-owned applications"
#                                            (Graph Explorer, Microsoft Graph Command Line Tools)
# These two are the documented ones; Microsoft operates more publisher tenants, so do not
# treat the pair as complete. The set grows ONLY by Microsoft documentation: a documented owner
# tenant, or an appId in Microsoft's service principal reference table
# (learn.microsoft.com/entra/identity/monitoring-health/reference-service-principal-table,
# "not exhaustive and will grow over time"). For any other owner tenant, name it with
#   GET /tenantRelationships/findTenantInformationByTenantId(tenantId='<appOwnerTenantId>')
# but a Microsoft-looking displayName is free text and promotes nothing: hold it, do not drop
# it. The daily-updated community list at github.com/merill/microsoft-info (keyed by appId)
# is the cross-check.

# Splunk (Azure Monitor diagnostic export shape: category / properties.*; tune field
# names to your add-on). Publisher filter lives in the sign-in subsearch, not in stage 2.

index=* category=MicrosoftGraphActivityLogs earliest=-30d@d latest=now
    [ search index=* category=ServicePrincipalSignInLogs resultType=0
        properties.servicePrincipalId="00000000-0000-0000-0000-000000000000"
        earliest=-30d@d latest=now
      | where NOT 'properties.appOwnerTenantId' IN ("f8cdef31-a31e-4b4a-93e4-5f571e91255a",
            "72f988bf-86f1-41af-91ab-2d7cd011db47")
      | stats count by properties.appId
      | fields properties.appId ]
| rename properties.appId as appId, properties.responseStatusCode as code,
    properties.requestUri as uri
| where tonumber(code)>=200 AND tonumber(code)<300
| stats count as ok2xx values(uri) as uris min(_time) as first max(_time) as last by appId

SP-less inventory — the class this incident belongs to. Pull the app-only sign-ins with the all-zeros ID, group by appId and the owner tenant printed on the record, and sort into three lanes. The full procedure, as four jobs (scoping, baselining, alerting, investigating) with the diagram and queries, is the companion note SP-less triage loop; it opens with a plain-language summary for readers new to service principals.

Lane 1 · Microsoft publisher

Ignore

Microsoft's own apps authenticate without a service principal by design. The sign-in record's appOwnerTenantId identifies them when it is a tenant Microsoft documents, or the appId is in Microsoft's reference table. A Microsoft-looking tenant name admits nothing.

Lane 2 · Known vendor

Watch

A grandfathered app reaching your tenant with no consent to revoke — a ConnectWise-shaped exposure. Admission is the vendor's exact defaultDomainName or a published appId, not a recognisable name. Re-check every baselined appId daily across all its sign-ins, zeros or real SP: new credential keyId, new resource, new ASN, failures. Hunt zeros → 2xx Graph activity (issuance-then-use) and the roles/credentials it touches (persistence audit).

Lane 3 · Unknown vendor

Diff daily, then file or block

Alert only on a new appId. Look it up: known → lane 2; Microsoft-named but undocumented, null owner, or no lookup result → hold; nobody's, lookup answered, second analyst → create a service principal for the appId, then disable it, record its objectId. Undo is deleting that SP. Breaks loudly if something depended on it — which is the point.

"Lateral movement" in this class is identity-side — role grants, credentials added to other apps, mailbox and Graph access — not host-to-host. The list is finite: Microsoft announced a block on SP-less auth for non-Microsoft multitenant apps for March 31, 2026, and its FAQ still lists "a few Microsoft and non-Microsoft applications" as exceptions; anything still doing it is one of those, so a non-Microsoft owner here is rare and high-prior. A zeros "Success" is issuance only; Graph is the one resource that then evaluates the empty token per request and logs it, which is why issuance-then-use runs on Graph activity. Scope: a vendor app you consented to has a real service principal and never appears in the zeros view; only the per-appId re-check sees its stolen credential used from new infrastructure.


# service-principal (app-only) sign-ins ONLY — user-log zeros are first-party apps refreshing
# tokens for users and carry the user's device IP; ignore them

index=* category=ServicePrincipalSignInLogs earliest=-90d@d
    properties.servicePrincipalId="00000000-0000-0000-0000-000000000000"
| rename properties.appOwnerTenantId as owner_tenant, properties.appId as app_id,
    properties.appDisplayName as app_name
| fillnull value="-" owner_tenant app_name
| eval bucket=case(
    in(owner_tenant, "f8cdef31-a31e-4b4a-93e4-5f571e91255a", "72f988bf-86f1-41af-91ab-2d7cd011db47"), "microsoft",
    owner_tenant="-", "hold: no owner on record",
    true(), "resolve")
| stats count min(_time) as first max(_time) as last values(properties.resourceDisplayName) as resources
    by bucket owner_tenant app_id app_name
| sort bucket

# fillnull matters: stats "by" silently drops rows where any by-field is null, so without it the
#   no-owner rows never appear
# bucket "microsoft" = documented Microsoft owner: expected, file as lane 1 (cross-check a few by
#   appId against Microsoft's service principal reference table / github.com/merill/microsoft-info)
# bucket "resolve": name owner_tenant with findTenantInformationByTenantId. Vendor's exact domain
#   or published appId = lane 2 (its breach lands here with no consent to revoke). Microsoft-named
#   but undocumented, lookalike domain, or no lookup result = hold. Nobody's, lookup answered,
#   second analyst = lane 3: create a service principal for the appId, then disable it (Microsoft's
#   documented block); verify via Graph that it exists with accountEnabled=false
# no Get-MgServicePrincipal step: an SP-less app has no service principal in your tenant to read
# Microsoft's own inventory call (reports FAQ, beta required; v1.0 returns no SP sign-ins):
#   GET /beta/auditLogs/signIns?$filter=signInEventTypes/any(t: t eq 'servicePrincipal')
#       and servicePrincipalId eq '00000000-0000-0000-0000-000000000000'

→ three jobs. SCOPING (daily): this query; a NEW (owner_tenant, appId) gets a lane. BASELINING (once per
  laned appId): baseline 90 days of ALL its sign-ins, zeros or real SP — credential keyIds, resources,
  ASNs, first seen — into the kept list. ALERTING (daily): every baselined appId against its row; new
  credential keyId outranks new ASN; failures from a new ASN count; append to the baseline only when
  a case closes, never rebuild it from raw.

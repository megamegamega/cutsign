ConnectWise Cloud Backup supply chain compromise

Stolen vendor app credentials for ConnectWise (ex-SkyKick) multi-tenant M365 applications were used from October 15 to mint Graph tokens across ~2,250 tenants (Microsoft; Huntress counted 300+ successful of ~1,000 observed). Microsoft attributed the campaign to Storm-0940 on October 21, operating the ARTEX agentic-AI framework.

On Cutsign: brief story 10-19 Storm-0940 attribution 10-22 CISO card IoC cards news & updates (live)

Verdict: hunt now if the ConnectWise app IDs ever touched your tenant — including former customers. This is credential abuse of a vendor's multi-tenant apps, not a patchable CVE: there is nothing to scan for, only logs to review. Sophos reports the token sweep reached tenants with no active backup subscription, so past use counts. ConnectWise disabled the seven app identities, but previously issued tokens may remain usable until they expire, and attacker persistence (added credentials, role grants) survives the vendor-side fix.

30-second read

Password spraying (151,000+ failures, Oct 10–14) preceded abuse of stolen ConnectWise application credentials from Oct 15: service-principal sign-ins from attacker infrastructure minting Graph tokens in customer tenants. Follow-on activity where sign-ins succeeded: directory reconnaissance, new client secrets planted on other applications (persistence beyond the ConnectWise apps), and privileged role changes including a service principal self-assigning Global Administrator. Conditional Access policies scoped to users often do not evaluate multi-tenant service-principal sign-ins — check yours rather than assuming coverage.

  • Conditional Access does not evaluate multi-tenant service-principal sign-ins

Infrastructure & discriminators

  • Token abuse: 144.172.64[.]128 · 144.172.64[.]99 · 144.172.64[.]60 · 144.172.94[.]243 (FranTech/PONYNET and related VPS)
  • Password spray: 187.15.88-90[.]x range, Oct 10–14
  • Suspicious-leaning user agents: Python-urllib/3.12 (enumeration and escalation tooling), python-requests/2.31 and 2.34.2 (targeted sweeps; the Oct 10–14 spray), curl/7.88.1 (Debian 12 python:3.12 container), azure-toolkit/1.0 (listed by Microsoft, not seen by Huntress) — expected vendor traffic is kiota-dotnet from Azure private IPv6. One Oct 13 browser user agent was missing its (KHTML, like Gecko) segment — a hand-set string
  • Low-confidence link: 194.165.16[.]21 (Huntress, on reuse of python-requests/2.31 only)
  • Operator tempo (Huntress, Oct 26 — scripted, with something adapting between runs): token requests to ~1,000 tenants one to six minutes apart (06:13–08:46 UTC Oct 15); ~100 failed token requests inside 10 s (06:04); a six-resource probe at exactly 4 s per tenant (13:54); credential replay at 13–21 requests/s against a 100-tenant list; post-change requests every 4–8 s for 22 min. Sub-second timestamps make these visible; minute-rounded exports hide them
  • Raw values: IoC corpus cards (16 + 11 indicators across the two stories)
  • All-zeros ServicePrincipalId (00000000-0000-0000-0000-000000000000) is Microsoft-documented service-principal-less authentication: "the service principal ID of an application making a service principal-less authentication is shown as 00000000-0000-0000-0000-000000000000 in the sign-in logs of the resource tenant" (Entra docs). A multitenant app obtains an app-only token from a tenant where it has no service principal object — no consent, no object ID claim, and in Microsoft's words "in most cases … harmless", except "where the target API has implemented improper authorization checks". That is the mechanism behind Chorus Cyber's observation: the campaign's token requests appear in tenants that never consented Cloud Backup; Chorus excludes those rows as noise. Read it the other way too: an all-zeros sign-in followed by successful Graph activity for the same appId is exactly the "improper authorization checks" case Microsoft warns about, and is a finding (inferred test below). Unresolved: Microsoft's retirement blocks SP-less auth for all non-Microsoft multitenant apps after March 31, 2026 (apps seen Feb 11–Mar 11 2025 were allowed until then; most others frozen April 2025) — all-zeros successful sign-ins for a third-party app in October 2026 should therefore not occur. Either enforcement is incomplete, the app was excepted, or the logged rows are blocked attempts (check resultType). Microsoft first-party apps still authenticate SP-less by design and show in user (mostly non-interactive) sign-in logs — expected, not this campaign; those records carry the user's device IP, so non-Microsoft ASNs there are normal. The question that matters is the service-principal (app-only) tab: all-zeros sign-ins whose appId resolves to a non-Microsoft publisher are grandfathered SP-less apps — a short, finite list worth a watch list

Do now

  • Query service-principal sign-ins for all seven appIds back to Oct 1 (review window Oct 13 → now at minimum)
  • Entra audit: credential additions, new owners, app-role assignments, consent grants, privileged role changes since Oct 13 — on all apps, not just ConnectWise ones
  • Pull user agents on any SP sign-ins found; Python/curl UAs from non-Azure IPs are the campaign shape
  • Verify tenant presence by Graph lookup per appId; confirm Conditional Access evaluates multi-tenant SPs
  • Review federated credentials on locally registered applications (guide §4) — issuer/subject trusts are persistence that survives secret rotation
  • Former customers: run the same checks — stale consents were swept too
  • Never a customer: filter the Service principal sign-ins tab for the all-zeros ID and the seven appIds; if present, apply Microsoft's documented block (create the service principal for that appId, then disable it) — defense in depth now that ConnectWise has disabled the identities, and it brings the app under Conditional Access

Escalation triggers

  • Any successful SP sign-in from the listed IPs or with the Python/curl UAs
  • Service principal self-assigning a directory role, or credentials added to unrelated apps
  • Credential or role churn on one app inside an hour (add → remove → add), a role granted to a sibling principal after a refused removal, or a service principal deleted after such changes — the Oct 26 Huntress persistence shape; also an anti-forensics tell
  • New IoCs or appIds published by ConnectWise / Microsoft
  • CISA advisory or broader MSP-tooling expansion of the campaign

Inferred detections — no Sentinel? same hunt, generic

The published queries above come first — Microsoft's KQL and the ConnectWise guide checklist supersede everything here. This is the fallback translation for environments without Defender XDR / Sentinel tables, over exported Entra logs in any SIEM or even a spreadsheet:

Service-principal sign-ins — the core question, tool-agnostic:

# exported Entra SP sign-in logs, Oct 1 → now
appId IN (the seven appIds above)
AND NOT (source = Azure private IPv6 AND user_agent = kiota-dotnet)
→ review every remaining row; Python/curl UAs from VPS space is the campaign

Persistence audit — a service principal doing admin things is the tell:

# Entra audit log, Oct 13 → now
operation IN ("Add service principal credentials", "Add member to role",
  "Update application", "Consent to application")
AND initiated_by is a service principal (not a user)
→ every hit gets a human review; self-role-assignment = incident

# Splunk (Azure Monitor diagnostic export shape: category / properties.*; tune field
# names to your add-on). Includes the REMOVE and DELETE operations: Huntress's Oct 26
# telemetry shows the persistence as churn and cleanup, not just additions.
index=* category=AuditLogs earliest=-30d@d
    operationName IN ("Add service principal credentials", "Remove service principal credentials",
      "Update application – Certificates and secrets management",
      "Add member to role", "Remove member from role",
      "Add app role assignment to service principal",
      "Update application", "Consent to application",
      "Remove service principal", "Delete application")
    properties.initiatedBy.app.servicePrincipalId=*
| rename properties.initiatedBy.app.displayName as actor_app,
    properties.initiatedBy.app.servicePrincipalId as actor_sp,
    properties.targetResources{}.displayName as target
| stats count values(target) as targets min(_time) as first max(_time) as last
    by actor_app actor_sp operationName

# churn: the same target gets an add AND a remove of credentials or roles inside 60 min
index=* category=AuditLogs earliest=-30d@d
    operationName IN ("Add service principal credentials", "Remove service principal credentials",
      "Add member to role", "Remove member from role")
| rename properties.targetResources{}.displayName as target, properties.initiatedBy.app.displayName as actor_app
| eval verb=if(match(operationName, "^Add"), "add", "remove")
| transaction target maxspan=60m
| where mvcount(mvdedup(verb))=2
| table _time duration target actor_app operationName
→ any churn pair is a hands-on operator (or an agent retrying); a failed cert upload followed by
  a successful one within a minute is the same tell

# sibling-principal grant + cleanup: role granted to one principal, then another principal deleted
index=* category=AuditLogs earliest=-30d@d
    operationName IN ("Add member to role", "Remove service principal", "Delete application")
| rename properties.initiatedBy.app.displayName as actor_app
| transaction actor_app maxspan=30m
| where searchmatch("Add member to role") AND (searchmatch("Remove service principal") OR searchmatch("Delete application"))
| table _time duration actor_app operationName

Issuance-then-use — tests the "no consent, no access" assumption instead of inheriting it (inferred; derived from the Chorus note above):

# stage 1: exported Entra SP sign-in logs, Oct 1 → now
service_principal_id = 00000000-0000-0000-0000-000000000000 AND result = success
→ set of appIds that obtained a token under an unresolved service principal
# stage 2: Graph activity logs, same window
appId IN (stage 1) AND response_status 200–299
→ any row = the app acted despite "no permissions"; review requestUri per appId
# prerequisite: Microsoft Graph activity logs must be ENABLED (diagnostic setting) — Huntress
# could not see them in affected tenants. If yours are off, stage 2 is a coverage gap, not a clean result
# noise: run stage 1 on service-principal (app-only) sign-ins ONLY — Microsoft first-party
# apps authenticate SP-less by design and surface in USER sign-in logs. Exclude apps whose
# publisher (AppOwnerOrganizationId / appOwnerTenantId) is a Microsoft tenant:
#   f8cdef31-a31e-4b4a-93e4-5f571e91255a  = "Microsoft Services" tenant (first-party apps
#                                            such as Edge Sync, Office 365 Exchange Microservices)
#   72f988bf-86f1-41af-91ab-2d7cd011db47  = Microsoft corporate (microsoft.com) tenant
#                                            (Graph Explorer, Graph Command Line Tools)
# These two are the documented ones; Microsoft operates more publisher tenants, so do not
# treat the pair as complete. Build the exclusion from data, not a list: for every appId in
# stage 1, resolve its service principal's appOwnerOrganizationId, then name that tenant with
#   GET /tenantRelationships/findTenantInformationByTenantId(tenantId='<id>')
# and exclude any whose displayName/defaultDomainName is Microsoft's. The daily-updated
# community list at github.com/merill/microsoft-info (MicrosoftApps.json) is the cross-check.

# Splunk (Azure Monitor diagnostic export shape: category / properties.*; tune field
# names to your add-on)
index=* category=MicrosoftGraphActivityLogs earliest=-30d@d latest=now
    [ search index=* category=ServicePrincipalSignInLogs resultType=0
        properties.servicePrincipalId="00000000-0000-0000-0000-000000000000"
        earliest=-30d@d latest=now
      | stats count by properties.appId
      | fields properties.appId ]
| rename properties.appId as appId, properties.responseStatusCode as code,
    properties.requestUri as uri, properties.appOwnerTenantId as publisher
| where tonumber(code)>=200 AND tonumber(code)<300
| where NOT publisher IN ("f8cdef31-a31e-4b4a-93e4-5f571e91255a",
    "72f988bf-86f1-41af-91ab-2d7cd011db47")
| stats count as ok2xx values(uri) as uris min(_time) as first max(_time) as last by appId
# if your Graph activity records lack a publisher field, resolve appId → publisher once via
# Get-MgServicePrincipal (AppOwnerOrganizationId) and keep the two Microsoft tenants out

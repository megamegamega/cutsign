eMudhra CA distrust

Eight eMudhra intermediate CA certificates were issued with private keys generated from single- or double-digit values — one key was literally the number 4 — making them trivially recoverable from the public certificates. Browsers and OSes blocked them October 17–20; Chrome removes the emSign ECC Root CA – G3 root entirely on the morning of October 27 (PT). Go tracks the trust-handling fix as CVE-2026-111943. eMudhra is exiting the global SSL/TLS business.

On Cutsign: brief story 10-21 Talos update 10-22 IoC card (9 — the cert hashes) news & updates (live)

Verdict: not an attack — an operational deadline. No malicious use of the weak keys has been observed (Talos), so the work is certificate inventory and replacement, not hunting. The real event is October 27: when Chrome drops the G3 root, legitimate certificates chaining to it stop working, and clients with independent trust stores (VPNs, proxies, CI/CD tooling, appliances, embedded devices) stay silently trusting the compromised intermediates until someone updates them. Expect PKIX/TLS failures to surface as "mystery outages" — have the answer ready before the tickets arrive.

30-second read

The eight intermediates (six TLS, two code signing) were issued in April 2025 with P-384 private keys generated from values below 256 — anyone can recover them and forge trusted certificates or sign code. eMudhra revoked the certificates; Chrome, Firefox, Apple and Microsoft blocked them Oct 17–20; Mozilla removed the root Oct 20; Google removes the root from the Chrome Root Store Oct 27 and is reviewing eMudhra's remaining roots. The attack risk is real but theoretical so far; the availability risk is scheduled.

Exposed if

  • Any certificate in your estate (or your vendors') chains to emSign ECC Root CA – G3 — it breaks in Chrome Oct 27
  • Software with its own or embedded trust store, or no revocation checking: VPN clients, proxies, CI/CD, appliances, embedded — still trusts the compromised intermediates
  • Go builds below 1.27.3 / 1.26.10 (crypto/x509 trust handling, CVE-2026-111943)

Not exposed if

  • Browser/OS platform trust stores — already blocked and updated
  • Updated bundles: NSS 3.131.1+, current Ubuntu ca-certificates and equivalents
  • No certificates chaining to eMudhra/emSign roots anywhere in the estate

Do now (before Oct 27)

  • Inventory certificates chaining to emSign/eMudhra roots — servers first, then API clients, CI/CD runners, proxies and appliances
  • Replace affected chains with another trusted CA before the Chrome removal
  • Update independent trust stores: Go toolchains, ca-certificates bundles, NSS, vendor appliances
  • Test critical clients against the disclosure site's test hosts
  • Pre-brief the help desk: Chrome cert errors starting Oct 27 have a known cause — and never "fix" them by disabling certificate verification

Escalation triggers

  • Any observed malicious use of the weak-key intermediates (forged TLS or signed code)
  • Forged certificates appearing in CT logs
  • Google distrusting eMudhra's remaining roots (review underway)
  • Oct 27: breakage reports → availability response, not security response

Inferred detections — while you wait

No scanner content exists because this is a trust problem, not a CVE scan. Everything below is doable today with standard tooling:

Spot-check any endpoint's chain — one-liner per host:

openssl s_client -connect host:443 -showcerts </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer
# flag any issuer containing "emSign" or "eMudhra"

Estate-wide inventory — if you run TLS inspection or Zeek, the data already exists:

# Zeek x509.log / TLS-inspection metadata
certificate.issuer contains ("emSign" OR "eMudhra")
→ before Oct 27: that's the replacement worklist
→ after Oct 27: a NEW cert chaining to the weak intermediates = forgery, escalate

Exact-match sweep — the eight compromised intermediates by hash:

compare observed intermediate cert SHA-256 against the eight published
hashes (on the IoC card) in proxy/Zeek logs and local trust stores
# also: flag code signed by the two code-signing intermediates

Java4Shell: OpenJDK Base64 decoder RCE

An out-of-bounds heap write in the JVM's hardware-accelerated Base64 decoder — CVE-2026-114938, scored 8.1 by Oracle (CVSS 3.1, high attack complexity), 9.8 preliminary by Red Hat and 9.2 by the finders (CVSS 4.0) — fixed November 17 in Oracle's November Critical Security Patch Update and the OpenJDK advisory. It needs an OpenJDK-based runtime 17.0.6 or later on an x86-64 CPU with AVX-512 VBMI. The finders, Calif, report code execution without a login against default configurations of Keycloak, Jira, Confluence, JFrog Artifactory, Jenkins and PingFederate; they published a trigger that proves the overwrite and are withholding the per-product exploit chains. As of Nov 22 attempts are reported, and no source confirms a compromise: watchTowr reports scanning with the User-Agent string java4shell-recon and blind exploit attempts against its honeypots, and Previdian counted nine attempts on five sensors (both via The Hacker News). The CVE is not in CISA's KEV catalog as of the Nov 20 release; CISA issued a patch-now alert on Nov 17.

On Cutsign: Java4Shell story 11-18 Oracle CSPU story 11-18 CISO card IoC card: none published news & updates (live)

Verdict: patch outside the normal cycle, and set the JVM flag today wherever a fixed build does not exist yet. This is memory corruption reachable before the login in the runtime under identity providers, CI servers and artifact stores — the systems that hold everyone else's credentials. Exposure is narrow and quick to scope: three checks (runtime version, CPU feature, untrusted Base64 on the path) rule most hosts in or out. The clock is the exploit, not the patch: the trigger is public, the malformed input sat in a public OpenJDK pull request from Sept 9, at least two labs say they have working remote exploitation (Calif; Wiz), and Calif says it will publish its chains. Fixed builds now exist from Oracle, Amazon Corretto, Azul, Eclipse Temurin, Red Hat (RHEL 8, 9 and 10), Debian and Ubuntu, and the Keycloak 26.8 images are rebuilt. What still lags is the runtime bundled inside other products and images not yet rebuilt: on Nov 22 Red Hat still listed its build of Keycloak, JBoss EAP, AMQ Broker and its Jenkins images as affected — there the one-flag mitigation closes the gap. Hunting is thin (crashes and malformed Base64, no campaign indicators), so this is a patch event with a tripwire, not a hunt.

30-second read

Once java.util.Base64 decoding gets hot, the JIT compiler swaps in a hand-written AVX-512 VBMI routine. A padded tail whose length is not a multiple of 4 drives its output length below zero, and a full 64-byte store lands up to 62 bytes past the destination array on the Java heap before the decoder rejects the input. The attacker picks where the bytes land, not their values; Calif's follow-on step ("JavaBleed") turns that into memory read and write. Triggering input is at least 65 characters on Java 21, 25 and 27 and at least 129 on Java 17 (Endor Labs). Many servers decode Base64 before checking the login — Basic-auth headers, SAML artifacts, CSRF tokens, cookies — and a Java client that connects out to a malicious TLS server is reachable too (Calif). A failed attempt can crash the JVM and the attacker can usually retry; a crash is far easier to cause than code execution (Datadog).

Interim mitigation — if a fixed build is not running yet

From the finders, repeated by Red Hat, Keycloak, Temurin and Rapid7; the OpenJDK advisory itself prints no workaround. Each needs a JVM restart and neither replaces the patch.


# preferred: turns off only the accelerated Base64 routine (may slow heavy Base64 workloads)

-XX:-UseBASE64Intrinsics

# alternative, x86-64 ONLY: turns off all AVX-512 use. An ARM64 JVM given this flag fails to start

-XX:UseAVX=2

# where to set it for Keycloak (shell, systemd, container -e, Operator custom resource spec.env)

JAVA_OPTS_APPEND=-XX:-UseBASE64Intrinsics

# the Keycloak Operator is a separate JVM; this does not cover the Keycloak pods

JDK_JAVA_OPTIONS=-XX:-UseBASE64Intrinsics

# prove it on the running process, not on the environment variable

jcmd <pid> VM.flags -all | grep -F UseBASE64Intrinsics      # expect: bool UseBASE64Intrinsics = false

Exposed if — all three

  • Runtime: an OpenJDK-based build 17.0.6 or later without the fix (17, 21, 25, 27 lines, any vendor), or Oracle Java SE 8 Enterprise Performance Pack 8u511b33-perf
  • CPU: x86-64 exposing AVX-512 VBMI — Intel Xeon Ice Lake, Sapphire, Emerald and Granite Rapids; AMD Zen 4 or newer; cloud VMs on those processors included
  • Data path: untrusted input reaches Base64.getDecoder() or getUrlDecoder(). Calif's tested list, stated as incomplete — no login: Keycloak, Jira, Confluence, Artifactory, Jenkins, PingFederate; with a login: Kafka broker, Solr, Elasticsearch, Gerrit, Spinnaker
  • Also: Java clients that open TLS connections to servers you do not control

Not exposed if

  • A fixed build is what the process is running (restarted since the update)
  • ARM64, or x86-64 without AVX-512 VBMI (Skylake-SP, Cascade Lake, AMD before Zen 4)
  • Java 8, Java 11, or OpenJDK 17.0.0 to 17.0.5
  • Mitigated, not fixed: the running JVM shows UseBASE64Intrinsics = false or is held to UseAVX=2

# Linux host check: exposed hardware prints all four flags

grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'

# which runtime a process is really on

jcmd <pid> VM.version

Hunt — published behaviors

  • A Base64 or Base64url token ending in = or == whose length is not a multiple of 4, in Authorization and Proxy-Authorization headers, cookies, token segments, query, form and JSON values. Length floor: 65 characters (Endor Labs; 129 on Java 17) or 32 (CrowdSec, Upwind) — the lower floor catches more and costs more noise
  • Bursts of IllegalArgumentException from java.util.Base64 in request-handling code (Endor Labs, Mend, Upwind)
  • JVM crash logs (hs_err_pid files): a SIGSEGV in a garbage-collection copy routine with a compiled Base64$Decoder.decode0 frame; unexplained restart bursts (Endor Labs, CISA)
  • Warm-up shape: a run of valid Base64 decodes from one source ahead of the malformed one, because the JIT must compile the decoder before the flawed routine is in use (Calif, Endor Labs)
  • Oversized or binary-looking responses from endpoints that echo decoded input (the memory-read step)
  • Rogue Java runtimes and suspicious Java child processes (CISA)

Upwind's caveat applies to all of these: none proves compromise, and their absence does not prove safety. No campaign infrastructure is published, so there is nothing to block by indicator.

Standing caveats: this is a runtime flaw, so dependency scans of application manifests do not see it (Endor Labs); host scans miss runtimes inside container images and vendor appliances; an authenticated scan reads the installed version, not whether the running process was restarted.

Do now

  • Scope with three checks: runtime 17.0.6 or later, x86-64 with AVX-512 VBMI, untrusted Base64 on the path. Count bundled runtimes in vendor products, container images and appliances; a software inventory often misses them
  • Patch to the vendor's fixed build and restart every JVM, internet-facing identity, CI and artifact services first; rebuild and redeploy container images
  • Where no fixed build exists yet (vendor-bundled runtimes, images not yet rebuilt), start the JVM with -XX:-UseBASE64Intrinsics and confirm it on the running process with jcmd
  • Restrict public access to Keycloak, Jira, Confluence, Jenkins and Artifactory login and management surfaces until they are patched or mitigated
  • Turn on the edge rule for malformed Base64 in log mode, review the matches, then block; it covers inbound HTTP only
  • Hunt back to Nov 17, and to Sept 9 where logs allow: malformed Base64 at the edge, decoder exception bursts, JVM crash logs, shells spawned by Java services

Escalation triggers

  • CISA KEV listing or a confirmed compromise (attempts against sensors are already reported) → emergency change for anything still unpatched and unmitigated
  • A product-specific exploit chain is published (Calif says it will) or a public code-execution exploit appears for a product you run
  • A JVM crash log with a Base64 decoder frame on an internet-facing service, or decoder exception bursts paired with malformed tokens from one source → incident lane
  • A Java service spawning a shell or download tool after such a burst → incident lane, treat its secrets as exposed
  • A vendor of a bundled runtime gives no fix date → keep the flag on and the exposure restricted

Inferred detections — while you wait

Vendors have shipped rules (Cloudflare, Talos, CrowdSec) and described behaviors (Endor Labs, Upwind, CISA), but nobody has published ready-made log queries. These translate the published behaviors into generic query logic. They are inferred: tune thresholds to your traffic before trusting them, and anything published above supersedes them.

Trigger shape at the edge — padded Base64 whose length is not a multiple of 4:


# web / proxy / WAF logs
token matches [A-Za-z0-9+/_-]{64,} followed by = or ==
AND length(token) mod 4 != 0
| count by src_ip, path → valid encoders never produce this shape

# most access logs do not record the Authorization header or cookies:
# a WAF or IDS rule in log mode is the better sensor for those fields

Decoder errors and crash canaries — the flawed routine rejects the input after the overwrite, and a miss crashes the JVM:


# application logs
IllegalArgumentException from java.util.Base64, burst per host per 10m

# host logs / file events
"A fatal error has been detected by the Java Runtime Environment"
new file hs_err_pid<pid>.log → open it: a Base64$Decoder.decode0 frame is the tell

After a hit, and mitigation coverage:


# EDR process lineage
parent.name = java AND child.name IN (sh, bash, curl, wget, nc, python*, cmd.exe, powershell.exe)
→ CI servers spawn shells by design: baseline per host, look for children that are new since Nov 17

# mitigation coverage
java process starts whose command line lacks -XX:-UseBASE64Intrinsics and -XX:UseAVX=2
→ a flag set through an environment variable does not show on the command line; jcmd is the proof

Splunk (index=*) / Elastic ES|QL (FROM logs-*) — CIM Web / Endpoint field names for Splunk, ECS for Elastic, Sysmon names for process and file events; tune to your add-on or integration:


# trigger shape at the edge: padded Base64 token, 65+ characters, length not a multiple of 4

index=* earliest=-14d@d (http_method=* OR uri_path=*)
| rex field=_raw max_match=10 "(?<b64>[A-Za-z0-9+/_-]{64,}={1,2})"
| mvexpand b64
| eval n=len(b64)
| where n % 4 != 0
| stats count as hits dc(b64) as tokens min(_time) as first max(_time) as last values(uri_path) as paths by src dest
| sort - hits

# decoder error bursts: 20 or more per host in 10 minutes

index=* earliest=-14d@d "IllegalArgumentException" ("java.util.Base64" OR "Illegal base64 character" OR "Input byte array has incorrect ending byte" OR "Last unit does not have enough valid bits")
| bin _time span=10m
| stats count as errors by host _time
| where errors >= 20
| sort - errors

# JVM crash canary in logs; with_decoder_frame counts crash text that names Base64

index=* earliest=-14d@d ("A fatal error has been detected by the Java Runtime Environment" OR "hs_err_pid")
| stats count as crashes count(eval(searchmatch("Base64"))) as with_decoder_frame min(_time) as first max(_time) as last by host
| sort - with_decoder_frame - crashes

# JVM crash log written to disk (Sysmon EID 11 / EDR file events)

index=* earliest=-14d@d TargetFilename="*hs_err_pid*.log"
| stats count as files min(_time) as first max(_time) as last values(TargetFilename) as paths by host Image

# Java service spawning a shell or download tool (Sysmon EID 1 / EDR)

index=* earliest=-14d@d ParentImage IN ("*/java","*\\java.exe") Image IN ("*/sh","*/bash","*/dash","*/curl","*/wget","*/nc","*/python*","*\\cmd.exe","*\\powershell.exe")
| stats count values(CommandLine) as cmds min(_time) as first by host ParentImage Image
| sort first

# mitigation coverage: hosts where a Java process started without either flag in the last day

index=* earliest=-24h Image IN ("*/java","*\\java.exe") CommandLine=*
| eval flagged=if(like(CommandLine, "%-XX:-UseBASE64Intrinsics%") OR like(CommandLine, "%-XX:UseAVX=2%"), 1, 0)

// trigger shape at the edge: padded Base64 token, 65+ characters, length not a multiple of 4
// (GROK keeps the first match in each event; the Splunk search keeps up to ten)

FROM logs-*
| WHERE @timestamp > NOW() - 14 days AND http.request.method IS NOT NULL
| GROK message "(?<b64>[A-Za-z0-9+/_-]{64,}={1,2})"
| WHERE b64 IS NOT NULL
| EVAL n = LENGTH(b64)
| WHERE n % 4 != 0
| STATS hits = COUNT(*), first = MIN(@timestamp), last = MAX(@timestamp), paths = VALUES(url.path) BY source.ip, destination.ip
| SORT hits DESC

// decoder error bursts: 20 or more per host in 10 minutes

FROM logs-*
| WHERE @timestamp > NOW() - 14 days AND message LIKE "*IllegalArgumentException*"
| WHERE message LIKE "*java.util.Base64*" OR message LIKE "*Illegal base64 character*" OR message LIKE "*Input byte array has incorrect ending byte*" OR message LIKE "*Last unit does not have enough valid bits*"
| EVAL bucket = DATE_TRUNC(10 minutes, @timestamp)
| STATS errors = COUNT(*) BY host.name, bucket
| WHERE errors >= 20
| SORT errors DESC

// JVM crash canary in logs; with_decoder_frame counts crash text that names Base64

FROM logs-*
| WHERE @timestamp > NOW() - 14 days
| WHERE message LIKE "*A fatal error has been detected by the Java Runtime Environment*" OR message LIKE "*hs_err_pid*"
| EVAL decoder = CASE(message LIKE "*Base64*", 1, 0)
| STATS crashes = COUNT(*), with_decoder_frame = SUM(decoder), first = MIN(@timestamp), last = MAX(@timestamp) BY host.name
| SORT with_decoder_frame DESC, crashes DESC

// JVM crash log written to disk (endpoint file events)

FROM logs-*
| WHERE @timestamp > NOW() - 14 days AND event.category == "file" AND file.name LIKE "hs_err_pid*.log"
| STATS files = COUNT(*), first = MIN(@timestamp), last = MAX(@timestamp), paths = VALUES(file.path) BY host.name, process.name

// Java service spawning a shell or download tool (endpoint process events)

FROM logs-*
| WHERE @timestamp > NOW() - 14 days AND event.category == "process"
| WHERE process.parent.name IN ("java", "java.exe") AND (process.name IN ("sh", "bash", "dash", "curl", "wget", "nc", "cmd.exe", "powershell.exe") OR process.name LIKE "python*")
| STATS count = COUNT(*), cmds = VALUES(process.command_line), first = MIN(@timestamp) BY host.name, process.parent.name, process.name
| SORT first

// mitigation coverage: hosts where a Java process started without either flag in the last day

FROM logs-*
| WHERE @timestamp > NOW() - 1 day AND event.category == "process" AND process.name IN ("java", "java.exe")
| EVAL flagged = CASE(process.command_line LIKE "*-XX:-UseBASE64Intrinsics*" OR process.command_line LIKE "*-XX:UseAVX=2*", 1, 0)
| STATS starts = COUNT(*), all_flagged = MIN(flagged), sample = VALUES(process.command_line) BY host.name
| WHERE all_flagged == 0
